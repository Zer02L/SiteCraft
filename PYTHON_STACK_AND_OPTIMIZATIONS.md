# 🐍 Python-Архитектура SiteCraft: Стек и Оптимизации

В данном документе описана архитектура, целевой технологический стек и комплекс инженерных оптимизаций для реализации мультисайтового движка (аналога **SiteCraft**) на **Python**, сохраняющего принципы автономности, изолированности баз данных и высокой плотности размещения сайтов на недорогих серверах.

---

## 1. Концепция и вызовы

Текущая реализация на **Go + PocketBase** работает по модели **Fleet of Binaries**:
* Каждый сайт клиента — это автономный легковесный процесс с собственной базой SQLite.
* Потребление памяти: **~20–35 МБ RAM** на сайт.
* Плотность: **40–50 изолированных сайтов** на базовом VPS (2 ГБ RAM / ~$10 в месяц).
* Развертывание: один статический бинарник без внешних зависимостей.

При переносе на **Python** стандартный подход («в лоб» через Django или FastAPI + Uvicorn) приводит к потреблению **80–150 МБ RAM** на процесс, что снижает плотность размещения в 3–5 раз. 

Ниже описан оптимизированный стек и архитектурные решения, позволяющие **сократить разрыв по ресурсам и производительности на 80–90%**.

---

## 2. Рекомендуемый стек (Python High-Density Stack)

Для минимизации оверхеда выбран модульный асинхронный стек без тяжелых ORM-абстракций:

| Компонент | Выбранный инструмент | Альтернатива «в лоб» | Обоснование выбора |
|---|---|---|---|
| **Веб-фреймворк** | **Litestar** (или **Starlette**) | FastAPI / Django | В разы легче FastAPI, нет тяжелой кодогенерации OpenAPI на каждый запуск, быстрый DI |
| **ASGI-сервер** | **Granian** (Rust + Hyper) | Uvicorn / Gunicorn | Написан на Rust, обходит ограничения GIL при парсинге HTTP, максимальный RPS и низкий TTFB |
| **Event Loop** | **uvloop** | Стандартный `asyncio` | Быстрый цикл событий на базе libuv (производительность на уровне Node.js/Go) |
| **Работа с БД** | **aiosqlite** + сырой SQL / **Peewee** | SQLAlchemy / Django ORM | Минимальный отпечаток в памяти, нулевой оверхед сложных мапперов |
| **Сериализация** | **msgspec** | Pydantic v2 | В 2–5 раз быстрее Pydantic, микроскопическое потребление RAM при валидации |
| **Шаблонизатор** | **Jinja2** (с предкомпиляцией) | Django Templates | Быстрый рендеринг SSR, полная совместимость с HTMX и Alpine.js |
| **Интерактивность** | **HTMX** + **Alpine.js** | React / Vue SPA | Сохранение Zero-JS / Low-JS парадигмы текущего SiteCraft |
| **Стилизация** | **Tailwind CSS v4** (Oxide) | — | Предкомпилированный CSS < 20 КБ без Node.js рантайма на сервере |
| **Админ-панель** | **SQLAdmin** / **FastAdmin** | Django Admin | Легковесная админка поверх ASGI без необходимости тянуть монолит Django |
| **Менеджер пакетов** | **uv** (Astral) | pip / poetry | Мгновенная установка зависимостей (< 1 сек), детерминированные lock-файлы |

## 3. Комплекс инженерных оптимизаций

### Оптимизация №1: Снижение потребления памяти процесса (до ~35–45 МБ)

Чтобы сократить аппетит одного процесса Python со стандартных 100–120 МБ до величины, близкой к Go:

1. **Отказ от тяжелых ORM:**
   * Использование легковесных SQL-запросов через `aiosqlite` со структурами `msgspec.Struct`. Это экономит до 30–40 МБ RAM на процесс по сравнению с SQLAlchemy / Django ORM.
2. **Тюнинг сборщика мусора (Garbage Collector):**
   ```python
   import gc

   # Отключение автоматического сбора для неизменяемых объектов после старта
   gc.freeze()
   ```
   После импорта библиотек и инициализации маршрутов вызов `gc.freeze()` помещает существующие объекты в постоянное поколение, снижая накладные расходы Copy-on-Write (CoW).
3. **Тюнинг параметров SQLite (PRAGMA):**
   ```sql
   PRAGMA journal_mode = WAL;          -- Параллельное чтение без блокировок
   PRAGMA synchronous = NORMAL;        -- Высокая скорость записи при надежности
   PRAGMA cache_size = -2000;          -- Лимит кэша SQLite: не более 2 МБ на базу
   PRAGMA temp_store = MEMORY;         -- Временные таблицы в памяти
   PRAGMA mmap_size = 0;               -- Отключение mmap для предотвращения разрастания VIRT RAM
   ```

### Оптимизация №2: Архитектура «Fleet of Databases inside One Worker»

Если строгая изоляция на уровне Linux-процессов не является обязательной, применяется архитектурный паттерн **многобазовой маршрутизации внутри единого пула воркеров**:

```
                          ┌──────────────────────┐
                          │    Nginx / Caddy     │
                          │  (SSL / Reverse Proxy)│
                          └──────────┬───────────┘
                                     │ Host: auto.ru / clinic.ru
                                     ▼
                   ┌───────────────────────────────────┐
                   │    1 общий процесс Python         │
                   │    (Litestar + Granian)           │
                   │    RAM: ~120–150 МБ на ВСЕ сайты  │
                   └─────────────────┬─────────────────┘
                                     │ Dynamic SQLite Connection
             ┌───────────────────────┼───────────────────────┐
             ▼                       ▼                       ▼
      ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
      │ auto_data.db │        │clinic_data.db│        │ legal_data.db│
      └──────────────┘        └──────────────┘        └──────────────┘
```

#### Пример реализации Host-based роутинга:
```python
from litestar import Litestar, Request, get
import aiosqlite
import os

DB_POOLS: dict[str, aiosqlite.Connection] = {}

async def get_db_for_request(request: Request) -> aiosqlite.Connection:
    host = request.headers.get("host", "default").split(":")[0]
    db_path = f"fleet_data/{host}/data.db"
    
    if host not in DB_POOLS:
        if not os.path.exists(db_path):
            db_path = "fleet_data/default/data.db"
        conn = await aiosqlite.connect(db_path)
        conn.row_factory = aiosqlite.Row
        DB_POOLS[host] = conn
        
    return DB_POOLS[host]
```

**Эффект:**
* 50 клиентских сайтов обслуживаются **одним процессом**, потребляющим всего **~120–150 МБ RAM суммарно**.
* По плотности на сервер данный подход **превосходит Go** (где 50 процессов требуют 50 × 25 МБ = ~1250 МБ RAM).
* Изоляция данных сохраняется на 100% (у каждого клиента собственный файл SQLite).

### Оптимизация №3: On-Demand запуск и Idle Shutdown (Socket Activation)

Если сохраняется модель строгой изоляции процессов (Fleet of Processes):
Для 50 сайтов малого бизнеса 90% времени трафик отсутствует. Сайты не должны постоянно занимать оперативную память.

1. **Systemd Socket Activation / Caddy On-Demand:**
   * Процесс сайта не запущен в фоне постоянно.
   * Веб-сервер слушает входящий сокет. При поступлении запроса веб-сервер пробуждает процесс сайта (`systemd --user` или unix domain socket).
2. **Idle-автоостановка процесса:**
   В приложение внедряется middleware неактивности:
   ```python
   import asyncio
   import sys
   import time

   class IdleTimeoutMiddleware:
       def __init__(self, app, timeout_seconds=900):  # 15 минут
           self.app = app
           self.timeout = timeout_seconds
           self.last_activity = time.time()
           asyncio.create_task(self._watchdog())

       async def __call__(self, scope, receive, send):
           self.last_activity = time.time()
           await self.app(scope, receive, send)

       async def _watchdog(self):
           while True:
               await asyncio.sleep(60)
               if time.time() - self.last_activity > self.timeout:
                   print("[SiteCraft] Idle timeout reached. Graceful exit.")
                   sys.exit(0)
   ```

**Эффект:**
* На сервере активно работают только те 2–4 сайта, куда зашли посетители.
* Фактическое потребление памяти на 50 сайтов: **~150–200 МБ RAM** вместо 4–6 ГБ.

### Оптимизация №4: Максимизация скорости (RPS и Latency)

1. **Сервер Granian (Rust):**
   * Запуск без Python-оверхеда на I/O-циклах:
     ```bash
     granian --interface asgi app:app --host 127.0.0.1 --port 8091 --opt
     ```
   * Сокращает TTFB (Time to First Byte) с типичных для Python 20–30 мс до **3–6 мс**.
2. **In-Memory кэш ответов (Read-heavy оптимизация):**
   * Страницы кэшируются в памяти словарем с TTL и мгновенно отдаются без обращения к SQLite.
   * Инвалидация кэша происходит по событиям обновления данных в админке.
3. **SSG (Статический экспорт):**
   * Для сайтов-визиток и лендингов выполняется пре-рендеринг в HTML (`python cli.py export --out ./dist`).
   * Статика отдается через Caddy / Nginx напрямую с диска с временем отклика **< 1 мс**.

### Оптимизация №5: Автономная поставка (Single-File / Self-Contained)

Чтобы приблизиться к удобству одного бинарника Go:
1. **Astral `uv`:**
   * Скрипт запуска со встроенными метаданными зависимостей (PEP 723):
     ```bash
     uv run --isolated sitecraft.py serve --port=8091
     ```
   * Установка всех зависимостей и изолированного Python происходит за доли секунды без ручного создания `venv`.
2. **Компиляция в бинарник через Nuitka:**
   * `nuitka --standalone --onefile --enable-plugin=pylint-warnings app.py`
   * На выходе получается скомпилированный бинарный файл ELF (C++ компиляция), который работает без установленного в ОС Python и запускается на 20–30% быстрее.

## 4. Сильные стороны Python-версии (В чём она превосходит Go)

1. **AI-First генерация контента и пресетов:**
   * Встроенные модули генерации сайтов «под ключ» по текстовому промпту клиента:
     ```python
     # Генерация полного лендинга на базе OpenAI / Claude / Ollama
     from instructor import from_openai
     from openai import AsyncOpenAI

     client = from_openai(AsyncOpenAI())
     preset = await client.chat.completions.create(
         model="gpt-4o-mini",
         response_model=NichePresetSchema,
         messages=[{"role": "user", "content": "Автосервис в Казани, ремонт АКПП"}]
     )
     ```
   * В Go реализация структурированного вывода LLM требует в 4–5 раз больше шаблонного кода.
2. **Гибкая система динамических плагинов:**
   * Возможность загружать пользовательские хуки, интеграции с CRM (Битрикс24, amoCRM) и платежными шлюзами без перекомпиляции основного ядра.
3. **Доступность расширений и кадров:**
   * Поддержка и верстка новых блоков на Jinja2 доступна широкому кругу специалистов любого уровня.
